## 3. 根因发现：368 个"漂移"里没有一个是真漂移

先做实测。真实 registry：21339 个模型，1735 个带 provenance。

用朴素的字符串比较，368 个模型的 stored recipe 与 fresh recipe 不一致：

```
stored: python main.py --model MLP --dataset circles --seed 42 --params 'hidden_layer_sizes=(50,)'
fresh : python main.py --model MLP --dataset circles --seed 42 --params 'hidden_layer_sizes=[50]'
```

**根因**：历史记录把 tuple 渲染为 `(50,)` / `(100, 50)`（Python repr），当前 `build_replay_command()` 渲染为 `[50]` / `[100, 50]`（JSON list，因为 provenance 经过 JSON 序列化）。

**关键判断**：这两种写法**指同一个超参数、训出同一个模型**。把它报成 "drift" 是**假阳性**——真正会误导运维者去重新训练 368 个完全没坏的模型。

但朴素的相等比较**没有能力**区分"拼写变了"和"语义变了"。本轮要补的就是这条分界线。

---

## 4. 解法

### 4.1 `core/replay_guard.py`（新，唯一实现源）

三段式漂移分级，取代布尔相等比较：

| 级别 | 含义 | 判据 |
|------|------|------|
| `none` | recipe 与今日代码输出一致 | 字符串完全相同 |
| `cosmetic` | 拼写不同，**指同一次运行** | 超参值**语义等价** + run-defining flag 相同 |
| `semantic` | **会训出不同的模型** | 超参值不同 或 run-defining flag 不同 |

三个关键判据：

1. **超参值语义归一化**：`(50,)` 与 `[50]` 归一为同一 tuple；`50` 与 `50.0` 归一为同一数值；序列统一归一为 tuple（不论原写作 tuple 还是 list）。
2. **run-defining flag vs visual-only flag 分离**：`--n-samples` / `--noise` **不进入 CLI 训练路径**（`main.run_experiment` 硬编码 `n_samples=500, noise=0.3`），只影响绘图。因此二者不同是 **cosmetic**，不是 semantic。
3. **`--params` 排除出 flag 比较**：它是可重复 flag，值已由超参映射单独比较；若纳入 flag 比较，**仅因参数顺序不同**就会误报。

`integrity_report()` 聚合 registry 全量；`verify_replay()` **实际执行** replay 并给出 verdict（DoD #4 "regression verification" 的另一半）。

### 4.2 接线（四端共用同一核心逻辑）

| 层 | 接口 |
|----|------|
| Registry | `RegistryManager.replay_integrity()` / `recipe_drift(model_id)` / `verify_replay(model_id)` |
| SDK | `MLDB.replay_integrity()` / `recipe_drift(model_id)` / `verify_replay(model_id)` |
| CLI | `python main.py model integrity`（全量审计）<br>`python main.py model verify <id>`（执行验证） |
| HTTP | `GET /api/provenance?integrity=1`（全量 / 带 id 为单模型）<br>`GET /api/provenance?verify=1&id=<id>`（执行验证） |

Flask (`web/server.py`) 与 Vercel serverless (`api/provenance.py`) 契约保持一致。

### 4.3 顺带修掉的一个真 bug

`RegistryManager.verify_replay()` 初版写成 `MLDB()`（无 registry base）→ 客户端会连到**真实 registry** 而不是当前 manager 的 registry。已修为 `MLDB(registry_base=self.registry_base)`。这是 `test_sdk_verify_replay_executes_the_replay` 抓出来的。

## 5. 实测（真实 registry）

```
$ python3 main.py model integrity

🧭 Replay integrity — 21339 registered model(s)
============================================================
   ✅ Recipe current:     20971
   🟡 Cosmetic drift:       368  (spelled differently, same run)
   ❌ Semantic drift:         0  (would reproduce a different model)

   Models with a frozen recipe: 1735 / 21339
   Stale text:  368  (21.2% of recipes)
   Broken:      0  (reproducibility actually lost)

   ✅ No model would reproduce a different run —
      every stale recipe still denotes the run it was frozen from.
```

| 指标 | 朴素字符串比较 | 本轮分级判定 |
|------|--------------|------------|
| 判定为"漂移" | 368 | 368（stale）|
| 其中**真**会训出不同模型 | 未区分 | **0** |
| 其中仅拼写不同 | 未区分 | 368 |

**结论：registry 的可复现性承诺目前没有破。** 368 个 stale recipe 全部只是拼写差异（tuple vs list 渲染），语义未变。

**这本身是本轮最有价值的产出**：把一个"看起来 368 个模型坏了"的告警，变成"0 个模型真的坏了，368 个只是拼写差异"——避免了 368 次无意义重训。

### 分级器的灵敏度验证

分级器**不是**"一味宽松"。测试用 6 个**真实语义漂移**场景验证它必须报警：换 dataset / 换 seed / 换 model 类型 / 换超参值 / 加超参 / 删超参 / 序列内容变化（`(50,)` → `(100,)`）。全部正确判为 `semantic` ✅

同时 4 个 cosmetic 场景必须**不**报警：tuple vs list、`C=1` vs `C=1.0`、`--n-samples`/`--noise` 差异、`--params` 顺序差异。全部正确判为 `cosmetic` ✅
