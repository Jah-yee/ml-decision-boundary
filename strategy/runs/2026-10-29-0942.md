本轮交付 **v13 DoD #7「CI 触发覆盖闭合」**：修复了一个**让 PR 静默失去 CI 验证**的触发块缺陷，

## 问题

### 根因

`.github/workflows/ci.yml` 的触发块：

```yaml
on:
  push:
    branches: [master, daily/*, fix/*, feature/*]
  pull_request:
    branches: [master]     # ← 过滤器
```

`pull_request` 上的 `branches: [master]` 意味着：**只有 base 为 `master` 的 PR 会启动 CI**。

本仓库 v13 采用 **stacked PR** 结构（base 是另一个 feature 分支），于是：

| PR | base | CI 运行？ |
|----|------|----------|
| #60 | `master` | ✅ 6/6 SUCCESS |
| #61 | `master` | ✅ 6/6 SUCCESS |
| #62 | `master` | ✅ 6/6 SUCCESS |
| **#63** | **`feat/v13-replay-provenance`** | ❌ **零次运行** |

### 证据

```
$ gh pr checks 63
no checks reported on the 'feat/v13-replay-integrity-guard' branch

$ gh pr view 63 --json statusCheckRollup
{"statusCheckRollup":[]}

$ gh run list --limit 15
2026-10-28 | pull_request | exp/dup-pr-probe            | success
2026-10-27 | pull_request | feat/v13-replay-provenance   | success
2026-10-26 | pull_request | feat/v13-provenance-provenance | success
2026-10-25 | pull_request | feat/v12-sdk-foundation      | success
（feat/v13-replay-integrity-guard —— 无任何记录）
```

对照组 `exp/dup-pr-probe`（base=`master`）**有** CI 运行 → 证明 CI 本身是好的，
唯一变量就是 base 分支。**根因锁定为触发块的 `branches:` 过滤器。**

### 为什么这个缺口特别危险

它**看起来不像故障**：

| 状态 | 视觉信号 | 人会不会注意到 |
|------|---------|--------------|
| CI 失败 | 🔴 红 | 一定会 |
| CI 在跑 | 🟡 灰 | 通常会等 |
| **零检查** | ⚪ **空白** | **大概率不会** —— 看起来像"还没开始" |

PR 页面上一片空白的 check 列表，和"CI 还没开始排队"在视觉上无法区分。
于是 v123 早场 / 晚场都把 `MERGEABLE` 读成了"已验证"。

> **MERGEABLE 说的是"能合并"，不是"已验证"。**
> `statusCheckRollup: []` 才是真相，而它一直就在那里，只是没人去问。

### 事实性错误修正

v123 两轮 run log 与 NEXT_ROUND_THEME 记录 "PR #63 OPEN + CLEAN + MERGEABLE"，
并把 CI 状态一并记为已验证。**对 PR #63 而言，"CI 6/6 SUCCESS"不成立 —— 实际是 0 次运行。**
本轮已在 ADR-0018 / NEXT_ROUND_THEME / 本 run log 中更正。

## 解法

### 1. 触发块：去掉 `pull_request` 上的 `branches:` 过滤器

```yaml
on:
  push:
    branches: [master, daily/*, fix/*, feature/*]
  # 无 'branches:' 过滤器 —— 见下方注释
  pull_request:
```

无过滤 = 任何 base 的 PR 都会启动 CI。

**不过度触发**：`push` 过滤器**不含 `feat/*`**，所以推 feature 分支不会触发重复的 push 构建，
只有 PR 事件会跑，一份构建。

### 2. `scripts/ci_trigger_audit.py`（新）—— 把不变量变成可执行门禁

读取 workflow 的 `on:` 触发块，回答 GitHub 会回答的那个问题：
**"一个 base 为 X 的 PR，会触发 CI 吗？"**

关键设计：

- **零第三方依赖**。PyYAML 在开发容器里有，但**不在 `requirements.lock`**，
  import 它会直接搞挂 CI。所以这里写了一个只覆盖 Actions 触发块这一种形状的子集解析器
  （嵌套一级 / flow list `[a, b]` / block list `- a`）。
  遇到看不懂的形状**抛异常而不是猜** —— 一个静默返回"无过滤器"的解析器会让审计**说谎**。
- **只读**。审计从不改写 workflow。修不修是人的决定，工具的职责是让缺口**可见**且**可测**。
- **可直接当 CI 门禁**：`exit 0` = 无缺口，`exit 1` = 有缺口。
- **顺带避开了 YAML 1.1 的坑**：PyYAML 会把裸 `on` 解析成布尔 `True`，
  自研解析器按字面 `on:` 查找，不受影响。

### 3. CI 新增 `ci-trigger-audit` job —— 自举守卫

这个 job **自己跑在 CI 里**，检查 CI 的触发块有没有被再次收窄。
一旦有人写回 `branches: [master]`，**构建会自己失败**。

```yaml
ci-trigger-audit:
  runs-on: ubuntu-latest
  timeout-minutes: 5
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: { python-version: '3.12' }
    - name: Audit CI trigger coverage
      run: python3 scripts/ci_trigger_audit.py
```

> 该 job **不执行** `pip install -r requirements.lock` —— 审计脚本只用标准库。
> 这很关键：**守卫不能依赖它要守护的那套环境**，否则两者会一起失效。

### 4. `tests/test_ci_trigger_audit.py`（新）—— 19 个测试

两类测试：

- **解析器行为**（12 个）：flow list / block list / 无过滤器 / 注释不被误认成事件 /
  行尾注释 / 缺 `on:` 抛异常 / GitHub 通配符语义（`*` 不跨 `/`、`**` 跨 `/`、`?` 单字符）/
  空过滤器不匹配任何分支 / `release.yml` 不算缺口 / CLI `--json` 输出可解析 / CLI 能检出缺口。
- **仓库自身不变量**（7 个）：`ci.yml` 的 `pull_request` 过滤器必须是 `None`
  （**最重要的一条**）/ 每个 base 分支都被覆盖 / 脚本 exit 0。

## 本轮最重要的产出

不是"加了 19 个测试"，而是：

> **把一个一直存在、但从未被测量的假设，变成了 CI 会主动拦住的门禁。**

在这次修复之前，"CI 覆盖了所有 PR" 是一句**没人验证过的话**。
它恰好在唯一一次不成立的时候（PR #63），静悄悄地失效了两轮。
现在它是一条**CI 每次都检查、违反就红**的规则。

一个副作用同样重要：**修复后，#63 及其之后的 PR 会首次真正获得 CI 验证。**
若合并时 CI 暴露了 #63 携带代码的真实问题，需单独跟进。
