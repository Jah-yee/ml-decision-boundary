## 问题

| base 分支来源 | 静态清单 | **PR 自身** |
| 判定 | 「base 会不会被覆盖」 | 「这个 PR **到底**有没有被验证」|

### 合并顺序死锁

```
#63  (head ci.yml 未修, base=feat/v13-replay-provenance)   ← 需要 CI 才能放心合并
  ↑ 被 #66 stacked

```

- 想让 #63 有 CI → 必须先把修复合进 #63 的分支
- 而修复在 #66 上，#66 的 base 又是 #63

**GitHub 不会把 #66 的文件变更「预演」到 #63 上。**

**从未被任何 CI 验证过**，而「CI 覆盖所有 PR」的承诺**在最需要它的那一个 PR 上依然不成立**。

> `MERGEABLE` 说的是"能合并"，不是"已验证"；`statusCheckRollup: []` 才是真相。

## 解法

### 1. `scripts/pr_coverage_audit.py`（新，唯一实现源）

把审计对象从「workflow 文件」升级为「PR」：

- **读 PR head 分支上的 workflow**：`git show <head>:.github/workflows/ci.yml`
- **用 PR 自己的 base 分支**去问「这份 workflow 会覆盖它吗」—— base **从 PR 自身读取**，不靠硬编码
- **复用 DoD #7 的解析器**（`from ci_trigger_audit import ...`），不重复实现 YAML 子集解析
- **零第三方依赖**（PyYAML 不在 `requirements.lock`）
- **只读**：不 merge、不 push、不改写 workflow
- **诚实降级**：拿不到 PR 列表时**报错退出（rc=2）**，绝不把「查不到」报成「一切正常」

### 2. 三个独立条件才算 `verified`

| # | 条件 | 回答的问题 |
|---|------|-----------|
| 1 | head 分支的 workflow 订阅了 `pull_request` | 有没有 workflow 会响应 |
| 2 | 它的过滤器覆盖**这个 PR 自己的** base 分支 | **会**不会跑 |
| 3 | GitHub **实际报告了** checks | **到底**跑没跑 |

② 是「会不会跑」，③ 是「到底跑没跑」—— **不可互相代替**。
只满足 ② 的 PR 仍会显示一片空白。

四种 verdict：`verified` / `base-not-covered` / `no-checks-reported` / `not-subscribed` / `unknown`。

### 3. CI 新增 `pr-coverage-audit` 自举 job

在 CI 里校验**所有 open PR** 都被覆盖 → 违反就红。

- 同样**不执行** `pip install -r requirements.lock` —— **守卫不能依赖它要守护的那套环境**
- 需要 `fetch-depth: 0`（要读各 PR 的 head 分支）+ `GH_TOKEN`
- CI job 数 7 → **8**

### 4. 落地 #63 的 CI：回移触发修复

把 DoD #7 的 `ci.yml` 修复 + `scripts/ci_trigger_audit.py` + 其 19 测试
**回移到 `feat/v13-replay-integrity-guard`**（= PR #63 的 head），push。

> **为什么选「回移修复」而不是「把 #63 的 base 改成 master」**：
> 回移让**每一个**分支都带上修复，对**下一个** stacked PR 同样有效；
> 改 base 只修好了这一个 PR，下一个 stacked PR 照样会踩同一个坑。
