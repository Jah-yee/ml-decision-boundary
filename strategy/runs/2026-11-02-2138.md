## 问题

上一轮（v127 早场）给 `scripts/pr_coverage_audit.py` 加了 `--require-checks`
「CI gate mode」。本轮开工实测发现：**这个号称「更严格」的门禁，实际比默认模式更宽松。**

上一轮的实现是这样判的：

```python
# --require-checks
missing = [c.number for c in coverages if c.observed_checks == 0]
if missing:
    return 1
return 0
```

而默认模式判的是 `summary["ok"]`，即**所有** `c.is_verified` 都为真。
`is_verified` 要求四件事同时成立：

| # | 条件 |
|---|------|
| 1 | head 分支的 workflow 订阅了 `pull_request`（`workflow_subscribes`） |
| 2 | 该 workflow 的过滤器覆盖**这个 PR 自己的** base 分支（`base_covered`） |
| 3 | GitHub 实际报告了 checks（`observed_checks > 0`） |
| 4 | 审计得出了结论（无 `problems`） |

**严格模式对第 1、2 条完全不看。** 于是：

```
PR 状态                observed_checks   默认模式   --require-checks
not-subscribed              7              FAIL          PASS    ← 错了
base-not-covered            7              FAIL          PASS    ← 错了
```

一个 **CI 从来不会为它触发**的 PR，只要身上还挂着**上一次运行留下的陈旧 checks**，
就能从号称「更严格」的门禁里溜过去。

**一个比默认模式更宽松的门禁，看上去像安全网，实际是个筛子** ——
而且它是那种「今天跑绿、明天出事」的筛子：只有当某个 PR 真的处于
unverified 状态时才会漏，而这恰恰是最需要门禁生效的时刻。

## 顺带挖出的元缺陷：遗留的测试是同义反复

v127 早场遗留的 `TestRequireChecks` 测试类**看起来**在测 `--require-checks`，
实际上它把判定逻辑**在测试里重新实现了一遍**：

```python
# Simulate the CLI's --require-checks decision logic
def require_checks_gate(coverages):
    missing = [c.number for c in coverages if c.observed_checks == 0]
    return 1 if missing else 0
```

这种测试**测的是测试自己** —— 把 CLI 的这个 flag 整个删掉，它们**照样全绿**。
它甚至把要修的 bug（只看 `observed_checks`）原样抄进了断言里，
于是**测试在保护 bug**：任何修复都会让它变红。

## 解法

### 1. 把「这个门禁过不过」收敛到唯一一个函数

```python
DEFAULT_REQUIREMENTS = ("subscribes", "base_covered", "checks", "auditable")

REQUIRE_CHECKS_REQUIREMENTS = DEFAULT_REQUIREMENTS + ("checks_completed",)
```

```python
def evaluate_gate(coverages, requirements=DEFAULT_REQUIREMENTS) -> dict:
    failures = {}
    for c in coverages:
        failed = [r for r in requirements if _requirement_failed(c, r)]
        if failed:
            failures[c.number] = failed
    return {
        "ok": not failures,
        "failed": sorted(failures),
        "failures": {n: failures[n] for n in sorted(failures)},
        "requirements": list(requirements),
    }
```

两种模式现在只做一件事：**传入不同的要求集合**。
因为 `REQUIRE_CHECKS_REQUIREMENTS` 是 `DEFAULT_REQUIREMENTS` 的**严格超集**，
单调性就由**构造**保证 —— 不再依赖两段代码「碰巧」写对。

### 2. 新增第五个要求：`checks_completed`

GitHub 在 workflow **开始**时就创建 check run，所以 `observed_checks`
把还在排队、还在跑的都算进去了。**「有 check」和「check 跑完了」是两件事**。

- `PrCoverage` 新增 `completed_checks` 字段 + `has_completed_checks` 属性
- 新增 `_count_completed_checks()`，按 `COMPLETED_CHECK_STATUSES`（结论词汇）
  与 `COMPLETED_CHECK_RUN_STATUSES`（`COMPLETED` 状态词汇）判定
- `to_dict()` 输出 `completed_checks`
- 报告行改为 `checks seen : 6 (6 finished)`

**一个实测出来的边界情况**：GitHub 会返回 `status=COMPLETED` + `conclusion=null`
的 check run（跑完了但没有结论）。第一版实现只认结论词汇，把这种 check 判成
「还没跑完」→ 严格门禁对这种 PR **永远不可能满足**。
修正为「结论是终态 **或** 状态是 `COMPLETED`」两条任一成立即算完成。

### 3. 测试全部重写为调用真实代码路径

新测试全部改为**调用真实的 `evaluate_gate()`**，并新增
**bug 回归测试**：把 `REQUIRE_CHECKS_REQUIREMENTS` 改回 `("checks",)`
（即重新注入原 bug），**必须有测试失败**。

实测（bug 注入验证）：

```
FAILED TestGateModel::test_strict_requirements_are_a_strict_superset
FAILED TestGateModel::test_strict_mode_is_never_laxer_than_default
FAILED TestGateModel::test_the_original_bug_is_fixed
FAILED TestGateModel::test_queued_checks_fail_the_strict_gate_only
4 failed, 35 passed
```

### 4. CI 接线：独立 job，而不是并行 job 里的一个 step

严格门禁要问「checks 跑完了吗」，这个问题**只有在兄弟 job 跑完之后**才答得上来。
实测 run `41314763785` 的时间戳：

```
pr-coverage-audit   completed 14:09:38
hyperparam-sweep   completed 14:11:11   ← 晚了 93 秒
```

8 个 job 是**并行**的。如果把 `--require-checks` 放进 `pr-coverage-audit` job 里，
它会看到兄弟 job 还在跑 → 门禁**因为错误的原因失败**（flaky，且必然在慢 job 上炸）。

所以严格门禁做成**独立 job** `pr-coverage-gate`，用 `needs:` 显式声明顺序：

```yaml
pr-coverage-gate:
  needs:
    - ci-trigger-audit
    - pr-coverage-audit
    - quality-gates
    - benchmark
    - depth-sweep
    - hyperparam-sweep
    - security-audit
    - quality-checks
```

**另一个坑**：CI 同时在 `push` 上触发，而 `github.event.pull_request.number`
在 push 事件上是空的 → `argparse` 报 `invalid int value: ''` → 门禁无故把构建弄红。
所以门禁 job 用 `if: github.event_name == 'pull_request'` 守卫，
并在非 PR 事件上显式 `exit 0` + `::notice::`。

> 教训：**门禁自身不能成为 flaky 源**。一个「要求所有 checks 都跑完」的门禁，
> 如果和被它检查的 checks 并行运行，就等于自己给自己设了一个定时炸弹。
> 顺序必须用 `needs:` 声明，不能指望运气。

## 设计约束（写进 ADR，下轮不得违反）

- **单一判定点**：两种模式共用 `evaluate_gate()`；新增模式必须通过**增加要求**实现，
  不允许另起一套判定表达式。
- **要求集合必须单调**：新模式的要求集合必须是旧模式的**超集**，
  由 `test_strict_requirements_are_a_strict_superset` 钉住。
- **未知要求必须报错**：`_requirement_failed()` 遇到未知要求名时 `raise ValueError`，
  不得静默通过。
- **门禁不得 flaky**：任何依赖「其他 job 已完成」的门禁必须用 `needs:` 显式排序；
  任何在 `push` 事件上无意义的要求必须有事件守卫。
- **诚实降级**：拿不到 PR 状态时仍然 rc=2（与 DoD #8/#15 一致）。

一个门禁如果比它要替代的模式更宽松，它就不是门禁，是**伪装成安全网的筛子**。
一个测试如果测的是自己，它就不是测试，是**给 bug 盖的图章**。
两者都是「看起来有、实际上没有」—— 而这恰恰是这一整轮在修的东西。
