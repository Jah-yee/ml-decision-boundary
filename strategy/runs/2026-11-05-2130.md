### 踩坑 1：GH007（私有邮箱）
第一次用 `git rebase` 重放后 push 被拒：
```
remote: You can make your email public or disable this protection
 ! [remote rejected] e3d5626 -> feat/v13-ci-trigger-coverage
```
**根因**：rebase 保留了 author，但 **committer** 被写成 `jydu_seven@outlook.com`（私有邮箱），
而原提交的 author 本来就是已验证的 `166608075+Jah-yee@users.noreply.github.com`。
**修法**：改用 `cherry-pick` + 显式设置 `GIT_COMMITTER_EMAIL` / `GIT_AUTHOR_EMAIL`
两个环境变量重建提交链 → author 与 committer 全部为公开 noreply 地址。

### 踩坑 2：`--force-with-lease` 的期望值要现读
第一次 push #67 时报 `stale info`：我以为远端 head 是 `f004255`，
实际远端是 `36a6dd3`（#67 上多一个 docs 提交）。
**修法**：`git ls-remote origin refs/heads/<branch>` 先读真实 sha，再作为 lease 期望值。
→ 推完**立刻回读校验**，不拿 push stdout 当证据。

### 踩坑 3：audit 解析的是**本地分支名**而不是 origin
修完 push 成功后重跑 audit，**依然报同样的缺陷**。
**根因**：`stack_topology_audit.py` 用 `git merge-base <branchA> <branchB>` 解析
**裸分支名**（不是 `origin/<branch>`），所以读到的是**未更新的本地分支**。
**修法**：`git fetch --prune` + `git branch -f <branch> origin/<branch>` 把本地分支对齐远端。
→ 这个坑值得记：**「push 成功」不等于「audit 能看见」**，验证工具的 ref 解析方式必须先确认。

### 踩坑 4：`filter-branch` 不接受裸 rev
`git filter-branch --env-filter ... -- 4372d70 ^4962d28` 报 `You must specify a ref to rewrite`。
改用 `cherry-pick` + 环境变量覆盖，更简单也更可控。

## 5. 本轮的元观察

「完成」和「交付」之间的缝，这轮又出现了一次，只是换了个位置：

- v130 早场修的是**「代码 staged 了但没 commit」**（代码 → 版本库）
- v131 晚场修的是**「版本库里有了但 PR 分叉了」**（版本库 → 可合并）

**两个缺陷在同一个位置：stack 的最后一环。** 6 个 PR 全部 CLEAN 全部 CI 全绿，
看起来「只差皇上点一下 Merge」—— 但**有一个 PR 实际上不可按建议顺序合并**。
绿色的 CI 和 CLEAN 的 mergeable 状态**都不能证明「能合并」**，只有拓扑审计能。

另一个观察：**「已修复」也需要证据**。push 成功 ≠ 审计器能看见（踩坑 3）。
中间还有一步「让本地 ref 对齐远端」，不补这一步，audit 会对着旧 ref 报旧缺陷，
让人误以为修复失败而去做多余的手工改动。
