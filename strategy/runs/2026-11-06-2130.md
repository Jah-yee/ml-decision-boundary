## 1. 缺陷根因（实测，非推测）

### 1.1 默认路径把「发布专用门禁」施加到 CI 工作流上

`scripts/release_audit.py:803`：

```python
paths = args.workflow or sorted(WORKFLOW_DIR.glob("*.yml"))
```

**不传 `--workflow` 时会审计 `.github/workflows/` 下所有 `*.yml`**，
即 `ci.yml` **和** `release.yml`。而 6 项门禁里有 3 项是**发布语义专属**的：

| 门禁 | 对 `ci.yml` 是否适用 | 实测结果 |
|------|---------------------|---------|
| `tag_discovery_safe` | ❌ 不适用（CI 不需要找上一个 tag） | ❌ 误报 |
| `changelog_not_truncated` | ❌ 不适用 | ✅ 通过（无 byte 截断） |
| `concurrency_declared` | ❌ 不适用（CI 并发正常） | ❌ 误报 |
| `actions_pinned` | ✅ 适用（但 CI 用的是 `actions/checkout@v4`） | ❌ 误报 |
| `permissions_explicit` | ✅ 适用 | ❌ 误报 |
| `trigger_safe` | ❌ 语义相反（CI **应该** push 到 master 就跑） | ❌ 误报 |

`ci.yml` **6 项全挂**，而它**没有任何缺陷**。

### 1.2 语义反转的门禁最危险

`trigger_safe` 要求「push 必须带 `tags:` 过滤器」。
这条规则对**发布**流水线是**对的**（否则每 commit 都发一次 release），
但对**CI** 是**反的**——CI 本来就该在 push 到 master 时跑。

**一个把「CI 的正确行为」判成「缺陷」的审计，比没有审计更糟。**

### 1.3 CI job 恰好绕开了这条路径（但这是运气，不是设计）

`.github/workflows/ci.yml:168`：

```yaml
run: python3 scripts/release_audit.py --workflow .github/workflows/release.yml --strict
```

**CI 显式指定了单个文件**，所以 CI 会绿。
但这意味着：

- 脚本的**默认行为是坏的**，只是 CI 恰好没用它；
- 谁要是手敲 `python3 scripts/release_audit.py --strict`，会拿到一个**假的失败**；
- 审计覆盖面的「入口」和「被审计对象」**由一行 YAML 决定**，而不是由审计器自己保证。

**「CI 绿」不等于「工具正确」。** 上一轮拿 CI 配置当验收证据，
而 CI 恰好绕开了唯一的 bug。

### 1.4 测试为什么全绿（68 passed）

68 条测试**没有一条**走「默认 glob 全目录」这条真实路径：

- `TestCli` 的 4 条全部显式传 `--workflow`；
- `TestRealRepository` 的 10 条全部只审计 `release.yml`。

**测试断言的是「审计器现在说的东西」，而不是「真实仓库里会发生什么」。**
这正是上一轮 theme 里自己写下的教训（「测试比审计先发现，是因为测试断言的是对的东西」），
**却在同一个文件的同一个 PR 里又犯了一次。**

## 2. 修复设计

### 2.1 引入「工作流种类」分类

不再按「文件路径」区分，而按**语义**区分：

```python
KIND_RELEASE = "release"   # 产出对外发布物：需要 tag 发现 / changelog / concurrency
KIND_CI = "ci"             # 跑测试：需要 permissions / action 钉 SHA / 合理的 trigger
```

判定依据（**可测试的规则，不是文件名约定**）：

- 有 `tags:` 过滤器 → `release`
- 名字含 `release` **或** 持有 `contents: write` → `release`
- 否则 → `ci`

### 2.2 每种 kind 适用各自的要求集

| 门禁 | release | ci |
|------|:---:|:---:|
| `tag_discovery_safe` | ✅ | ➖ 不适用 |
| `changelog_not_truncated` | ✅ | ➖ 不适用 |
| `concurrency_declared` | ✅ | ➖ 不适用 |
| `actions_pinned` | ✅ | ✅ |
| `permissions_explicit` | ✅ | ✅ |
| `trigger_safe` | ✅（要求 tags 过滤） | ✅（要求**非** tag-only trigger） |
| `tag_pattern_anchored`（strict） | ✅ | ➖ 不适用 |

**关键：`trigger_safe` 的语义按 kind 反转。**
CI 不该有 `tags:` 过滤器（那会让 CI 永不触发）；
release 必须有（否则每 commit 发一次）。

### 2.3 单调性必须**跨 kind** 保持

上一轮的强约束是「严格集合 = 默认集合的**严格超集**」。
引入 kind 后必须升级为：

> **对每一种 kind**，strict 要求集 ⊇ default 要求集，且 strict 多出至少一项。

即 `STRICT_REQUIREMENTS[kind] ⊋ DEFAULT_REQUIREMENTS[kind]`，
且 `STRICT[kind] ⊆ STRICT[release]`（strict 项只对 release 有意义）。

**测试必须显式断言这一点**，否则「分 kind」就成了绕过门禁的后门。

### 4.2 `.github/workflows/ci.yml` —— 修复审计新发现的真实缺陷

**审计器分类生效后，暴露出一个此前从未被发现的真实缺陷：**
`ci.yml` **完全没有声明 `permissions:` 块**。

这意味着 CI 的 `GITHUB_TOKEN` **继承仓库默认权限**——在多数仓库上默认是
「read and write」，也就是**每一个 CI job 都拿着写权限跑，而它们一个都不写东西**。

修复（最小权限）：

```yaml
permissions:
  contents: read        # actions/checkout 需要读仓库
  pull-requests: read   # pr-coverage-audit / pr-coverage-gate 用 GITHUB_TOKEN 读 PR
```

**不授予任何 `write` scope**——没有 CI job 需要 push、评论或发布。

> ⚠️ 这是本轮**第二个**真实缺陷，而它**只能被「先修好审计器」暴露出来**：
> 上一轮的审计把 `ci.yml` 判成 6 项全挂（含 4 项误报），
> **没人会去修一个「到处都是红」的结果**——真缺陷被淹没在噪音里。
> **一个把对的东西判成错的审计，会让真缺陷变得看不见。**

## 6. 元观察

### 6.1 「上一轮说通过了」和「现在能通过」是两件事

上一轮的 theme 白纸黑字写着
「`release_audit --strict` **exit 0（6/6）**」。
**实测是 exit 1。**

差异不在「运气」，在于**执行路径不同**：
上一轮大概率跑的是
`release_audit.py --workflow .github/workflows/release.yml --strict`
（**单文件**，绕过了 bug），
而「`release_audit --strict`」（**默认 glob**，会带上 `ci.yml`）是 exit 1。

**验收命令的写法，决定了验收是否有效。**
一个只验「我指定的那条路径」的验收，
和**没验**在信息量上几乎没有区别。

### 6.2 CI 绿 ≠ 工具对

CI job 恰好显式传了 `--workflow .../release.yml`，**恰好**绕开了唯一的 bug。
所以**上一轮是有 CI 证据的**——而那个证据是**无效的**。

**CI 绿只证明「CI 跑的那条路径是绿的」，不证明「工具的默认行为是对的」。**
CI 是**执行者**的证据，不是**设计者**的证据。

### 6.3 「把对的东西判成错的审计，会让真缺陷变得看不见」

这是本轮最值钱的一条。

上一轮的审计把 `ci.yml` 判成 **6 项全挂**——其中 4 项是**误报**
（CI 不需要 tag 发现 / 不需要 release concurrency / CI 用 `actions/checkout@v4` 没错 /
CI 不该有 `tags:` 过滤）。

**当审计结果「到处都是红」时，没人会去分辨哪几颗是真的。**
于是 `ci.yml` 真正缺 `permissions:` 块这个**真实缺陷**，
被淹没在 4 颗假警报里，**没人看见**。

修好分类之后，`ci.yml` 只剩 **1 项红**——**而那一项是真的**。

**误报不只是噪音。误报是有害的：它消耗的是「信噪比」，
而信噪比是发现真缺陷的唯一预算。**

### 6.4 分类不能成为后门

新增的 6 条 bug 注入测试专门盯这件事：
一个 workflow **曾经**是 release、后来丢了 `tags:` 过滤——
它**仍然**持有 `contents: write`，所以**仍然**按 release 规则判定，
**仍然**会被 `trigger_safe` 抓到。

**「按 kind 豁免某些检查」天然是一条后门。**
必须用测试把门焊死，否则下一轮就会有人「顺手」豁免掉真正该查的东西。
