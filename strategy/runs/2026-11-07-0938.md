## 1. 选题依据：本轮主题不是「又抓一个 bug」，而是「抓一整类 bug」

上一轮（v133 晚场）修好了 `ci.yml` 缺 `permissions:` 的真实缺陷，并在 run log 里写下：

> 修好后只剩 1 项红，**而那一项是真的**。

这一轮第一个念头是：**那个「红」有守卫吗？**

答案是：**没有。** 而且不是「暂时没有」，是**结构性地没有**——而且这件事在被发现之前，已经**静默生效了整整一轮**。

## 2. 缺陷的精确形态：审计 job 跑了，但没覆盖它声称守护的产物

`.github/workflows/ci.yml` 的 `release-audit` job 当时是：

```yaml
- name: Audit release pipeline
  run: python3 scripts/release_audit.py --workflow .github/workflows/release.yml --strict
```

`--workflow` 把审计**收窄到单文件**。而本仓有**两个** workflow：

- `.github/workflows/ci.yml` —— 11 个 job、PR 级门禁、token 权限
- `.github/workflows/release.yml` —— 唯一持 `contents: write`、唯一产出对外发布物的流水线

于是这个 job 的真实语义是：**「审计 release.yml」**，而它的名字和岗位宣称的语义是**「审计流水线」**。

`release_audit.py` 自己**有**默认 glob（`.github/workflows/*.yml`），**能**覆盖两个文件。**审计器没毛病，是调用方把它指错了地方。**

## 3. 实测证据：注入缺陷 → 所有审计全绿

### 3.1 注入

对 `ci.yml` 注入两个缺陷（这是 v133 刚修好的那个缺陷的**同一个**，外加一个解 pin）：

- 删除顶层 `permissions:` 块 → CI 的 `GITHUB_TOKEN` 继承仓库默认权限（多为 read-write）
- 把 `actions/checkout` 解 pin

### 3.2 跑 CI 里**原样**的命令

```
python3 scripts/release_audit.py --workflow .github/workflows/release.yml --strict
  → CI_RELEASE_AUDIT_EXIT=0        ← PASSED

python3 scripts/ci_trigger_audit.py    → exit 0
python3 scripts/job_graph_audit.py     → exit 0
```

**所有审计全绿。而 `ci.yml` 此刻正带着无守护的权限缺陷。**

### 3.3 对照实验：审计器**能**抓，纯粹是覆盖率问题

把同一个注入缺陷文件**直接**交给审计器：

```
python3 scripts/release_audit.py --workflow /tmp/ci_injected.yml --strict
  → ❌ release audit FAILED for: /tmp/ci_injected.yml
    /tmp/ci_injected.yml: permissions_explicit
    permissions_problems: ["no top-level 'permissions:' block declared"]
  → EXIT=1
```

**结论（这是本轮的第一根支柱）：** 审计器本身完全正常；缺陷 100% 在**覆盖率**——它从来没被指向那个文件。

### 3.4 于是上一轮的修复是**无守卫的**

v133 补上的 `permissions: contents: read` —— 没有回归防护。删掉它，CI 全绿。这不是「将来可能出问题」，是**此刻就是问题**，且已经**静默存在了一整轮**。

## 4. 本轮实现：不止改一行调用，而是闭合**整个缺陷类**

只把 `--workflow ...` 删掉能修掉**这一个**实例，但明天有人再加一个 `--workflow`，同样的洞会再开一次，而且更难找。

所以本轮新增**元审计** `scripts/audit_coverage_audit.py`：

> **当一个审计 job 运行时，它到底在看哪些产物？**

### 4.1 两项检测

| 检测 | 含义 |
|------|------|
| `coverage_narrowed` | 审计调用显式指定了 workflow 路径，而该路径集是仓库 workflow 文件集的**严格子集** |
| `workflow_uncovered` | 某个 workflow 文件**完全没有**被任何审计调用覆盖 |

### 4.2 关键设计决定：`pr_coverage_audit.py` **不在**受审名单里

第一版把 `pr_coverage_audit.py` 也列为受审脚本，结果它自己报了**假阳性**。

理由：**它审计的是「PR」，不是「workflow 文件」**。对它而言 `--workflow` 不构成覆盖率收窄。

这直接接上上一轮的元观察：**误报不只是噪音，误报是有害的**——假警报会把真缺陷淹掉。所以这里选择**窄而准**，而不是宽而全：只审**确实审计 workflow 文件**的脚本。

### 4.3 实现约束（沿用本仓既有约定）

- **纯 stdlib**，不引入 PyYAML（与 `release_audit.py` / `job_graph_audit.py` 一致）
- 自写 YAML 子集解析器
- **hermetic**：只读本仓文件，不触网、不碰 git、不调 GitHub API
- 门禁单调性由构造保证：两种模式共用唯一判定函数 `evaluate_gate()`，strict 要求集是 default 的严格超集

### 4.4 解析器的两次真实 bug（都是自己抓到的）

写完第一版，测试直接挂了 7 条：

1. **`- run: <cmd>` 解析不到** —— 正则 `(?:\s+-|\s+)run:` 里，`-` 与 `run:` 之间的空格没被吃掉 → 改为 `^\s*(?:-\s+)?run:\s*(.*)$`
2. **`run: |` 块标量解析不到** —— 更隐蔽：块体行（indent 10）会先命中「普通 step」分支（`indent >= 6`）并被 `continue` 吃掉，**永远到不了**块体处理分支 → 必须把块体分支**前置**

第 2 条值得单独说一句：**本仓每一个多行 CI step 都是 `run: |` 写的**。一个只会读 `- run: <单行>` 的解析器，在本仓会找到 **0 个**审计调用——而且它**不会报错**，只会安静地说「所有 workflow 都未被覆盖」。这正好是 v133 那条元观察的翻版：**静默降级比崩溃危险**。

### 4.5 strict 模式的一个语义澄清

`--strict` 要禁止**任何**收窄，即使该收窄恰好覆盖了全部文件。此时它**不是**覆盖率问题（问题列表为空），所以 strict 判定必须**从 invocations 读**，不能只从 problems 读。这条已用测试焊死。

## 7. 元观察

### 7.1 「有 CI 证据」和「CI 证据有效」是两件事

上一轮的主题文档白纸黑字写着「`release_audit --strict` exit 0（6/6）」——**看起来是好消息**。实际上 CI job 传的是 `--workflow release.yml`，**恰好**绕开了唯一的 bug。

**CI 是「执行者」的证据，不是「设计者」的证据。** 一个从没指向正确目标的检查，跑得再绿也是**零信息**——甚至更糟：它把「未检查」伪装成「已检查」。

### 7.2 覆盖率是**整体属性**，不可能靠逐个调用点自觉维护

上一轮已经发现过一次「四个『对的』排除叠加起来，让唯一高危面零覆盖」。那次的解法是**逐个**加排除的注释。

本轮是同一个形状的第二次出现：不是「四个排除」，是**一个收窄参数**。但性质完全一样：

> **局部看每一处调用都「有道理」，合起来却让一个高危面零覆盖。**

所以解法也不能是逐个自觉——必须是**一个机器检查**。这正是本轮新增元审计的理由。

### 7.3 审计器也要被审计

这是本轮最有意思的结构性观察：**审计器本身成了被审计对象。**

本仓已有 6 个审计器，它们都在审「产物」。现在多了一个审「审计器」的。它问的问题和其他审计**在结构上不同**：其他审计问「这个产物对吗」，它问「**这个审计真的看了它说要看的东西吗**」。

后者是前者的**前提**。一个收窄的审计器会把真缺陷变成「已检查」的假象——**它污染的不是自己的输出，而是其他所有审计的可信度**。

- **皇上 / 仓库维护者** —— CI 绿灯重新变得**可信**

- **未来的每一个贡献者** —— 收窄不再能静默通过

### 8.2 本轮实际交付的价值

1. **把一个无守卫的缺陷变成有守卫的** —— `ci.yml` 权限缺陷（v133 刚修）此前**删掉就绿**，现在删掉会红
2. **闭合了一整个缺陷类** —— 不只是这一个调用点；任何未来的收窄都会被自动抓住
3. **实证了「CI 绿 ≠ 证据有效」** —— 上一轮的主题文档里的「exit 0」是**无效证据**，本轮给出了对照实验
4. **32 条 hermetic 测试，含 bug 注入** —— 重新收窄 → 检出为真
5. **窄而准的误报控制** —— `pr_coverage_audit.py` 被排除在受审名单外，延续上一轮「误报是有害的」的教训

### 8.3 价值边界（诚实降级，不夸大）

- 本轮交付的是**「收窄不再能静默通过」**，**不是**「审计覆盖率已达最优」
- 本审计只覆盖**已知受审脚本**的显式 `--workflow` 收窄；它**不**检测以其他方式收窄（例如通过环境变量、软链、glob 模式限定）
- `ci.yml` 的权限修复**尚未经 CI 实跑验证**（需 PR 的 CI 跑完）
- **合并权归皇上**（`spec/CHARTER.md` 第 7 步），本轮只交付不合并
- **端到端发布仍未验证** —— 需要真实 tag，属需皇上决策的动作
